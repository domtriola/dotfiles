# Fine-grained GitHub tokens for Docker Sandboxes

Researched on 2026-10-08. All claims cite a primary source. Items that a primary source does not confirm are in [Open questions](#open-questions-and-unconfirmed-items).

## Question

What is the best way to automate the creation of a narrowly scoped GitHub token for each Docker Sandbox (`sbx`)? The starting point is GitHub's URL pre-fill feature for fine-grained personal access tokens (PATs).

## Summary

You cannot fully automate fine-grained PATs. GitHub has no REST or GraphQL endpoint that creates one, and the pre-filled URL still needs a person to select repositories and click **Generate token**. The pre-fill URL has no documented parameter for specific repositories.

**Recommended approach:** Register a private GitHub App on your account, and install it on the repositories that sandboxes can use. On the host, write a small helper that mints an installation access token. The helper uses `repositories` and `permissions` to limit the token to one sandbox's needs. Register the helper per sandbox:

```console
sbx secret set github --sandbox <name> \
  --command '/abs/path/gh-app-token --repo owner/repo --perm contents=write --perm pull_requests=write'
```

The `sbx` daemon runs the command on the host and caches the result for 55 minutes by default. Installation tokens expire after 1 hour. Thus the default cache refreshes the token before it expires, and you need no rotation hook. The token never enters the sandbox.

**Trade-offs:**

| Option | Fully automatic | Scope per sandbox | Acts as | Lifetime | Main cost |
| --- | --- | --- | --- | --- | --- |
| GitHub App installation token + `--command` | Yes | Repositories and permissions | The app (bot) | 1 hour, auto-refresh by `sbx` | You must keep the app private key on the host. Commits, PRs, and comments show the app as the author. |
| GitHub App user access token + `/token/scoped` | After one device-flow sign-in | Repositories and permissions | You | 8 hours; refresh token 6 months | Helper must store and rotate refresh tokens and needs the client secret. |
| Fine-grained PAT from pre-filled URL | No (manual click, manual repository selection) | Repositories and permissions | You | 1 to 366 days, or none | Limit of 50 tokens. Manual deletion. No owner API to delete. |
| `gh auth token` | Yes | None (OAuth scopes `repo`, `read:org`, `gist`) | You | Long-lived | All repositories that you can access. |

## Findings

### 1. URL pre-fill for fine-grained PATs

- **Base URL:** `https://github.com/settings/personal-access-tokens/new`. The documented example is `?name=Repo-reading+token&description=Just+contents:read&target_name=octodemo&expires_in=45&contents=read` ([GitHub Docs: Pre-filling fine-grained PAT details](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#pre-filling-fine-grained-personal-access-token-details-using-url-parameters)).
- **All parameters are optional.** The token generation form validates them, so that the combinations of permissions and resource owner make sense (same source).
- **Supported parameters** (same source, "Supported query parameters" table):
  - `name`: string, 40 characters or fewer, URL-encoded. Pre-fills the display name.
  - `description`: string, 1024 characters or fewer, URL-encoded.
  - `target_name`: user or organization slug. Sets the resource owner. The default is the current user.
  - `expires_in`: integer from 1 to 366, or `none`. The default is 30 days, or less if the target has a token lifetime policy.
  - `<permission>`: one query parameter for each permission, with the value `read`, `write`, or `admin`. Not every permission supports each level. `write` includes `read`, and `admin` includes `write`. Combine them as `&contents=read&pull_requests=write`.
- **Permission parameter names** (same source, "Permissions" tables):
  - Account permissions (only when the current user is the resource owner): `blocking`, `codespaces_user_secrets`, `copilot_messages`, `copilot_editor_context`, `copilot_requests`, `emails`, `user_events`, `followers`, `gpg_keys`, `gists`, `keys`, `interaction_limits`, `knowledge_bases`, `user_models`, `plan`, `private_repository_invitations`, `profile`, `git_signing_ssh_public_keys`, `starring`, `watching`.
  - Repository permissions: `actions`, `administration`, `artifact_metadata`, `attestations`, `code_quality`, `security_events`, `codespaces`, `codespaces_lifecycle_admin`, `codespaces_metadata` (read), `codespaces_secrets` (write), `statuses`, `contents`, `repository_custom_properties`, `vulnerability_alerts`, `dependabot_secrets`, `deployments`, `discussions`, `environments`, `issues`, `merge_queues`, `metadata` (read), `pages`, `pull_requests`, `repository_advisories`, `secret_scanning_alerts`, `secrets`, `actions_variables`, `repository_hooks`, `workflows` (write).
  - Organization permissions (only when the resource owner is an organization): names start with `organization_` (for example `organization_administration`), plus `issue_types`, `members`, and `team_discussions`. Only `organization_custom_properties` accepts `admin`. See the docs page for the full table.
- **Repository selection:** The parameter table has no parameter for "Only select repositories" or for specific repository names ([same source](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#supported-query-parameters)). The manual steps tell the user to choose **Repository access** and then pick repositories from the **Selected repositories** dropdown ([GitHub Docs: Creating a fine-grained PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token), steps 11 and 12). Thus you cannot pre-select repositories with a documented parameter.
- **Manual step:** The last step is "Click **Generate token**" ([same source](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token), step 14). The pre-fill feature only fills the form.
- **Organization approval:** If the resource owner is an organization that requires approval, the token is `pending` until an organization administrator reviews it. Until approval, the token can only read public resources. If you are an owner of the organization, GitHub approves the request automatically ([same source](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)).
- **Other limits:** "There is a limit of 50 fine-grained personal access tokens you can create." GitHub recommends a GitHub App for automations ([same source](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)). Each token can access the resources of only one user or organization ([GitHub Docs: Fine-grained PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens)). Fine-grained PATs cannot contribute to repositories where the user is an outside collaborator, cannot access Packages, and cannot call the Checks API ([same source, limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations)).

### 2. APIs for fine-grained PATs

- **No create endpoint.** GitHub's OpenAPI description has only these paths that contain `personal-access-token`, and all are under `/orgs/{org}/` ([github/rest-api-description, api.github.com.json](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)). It has no `/user/...` path for PATs. The REST docs list the same endpoints ([GitHub Docs: REST API endpoints for personal access tokens](https://docs.github.com/en/rest/orgs/personal-access-tokens)):
  - `GET /orgs/{org}/personal-access-token-requests`: list requests.
  - `POST /orgs/{org}/personal-access-token-requests` and `POST /orgs/{org}/personal-access-token-requests/{pat_request_id}`: approve or deny requests.
  - `GET /orgs/{org}/personal-access-token-requests/{pat_request_id}/repositories`.
  - `GET /orgs/{org}/personal-access-tokens`: list tokens with access to the organization.
  - `POST /orgs/{org}/personal-access-tokens` and `POST /orgs/{org}/personal-access-tokens/{pat_id}`: "Limited to revoking a token's existing access" (body `action: revoke`).
  - `GET /orgs/{org}/personal-access-tokens/{pat_id}/repositories`.
  - Each endpoint says "Only GitHub Apps can use this endpoint."
- **Deletion by the owner** is a manual step in Settings (**Developer settings > Personal access tokens > Fine-grained tokens > Delete**) ([GitHub Docs: Deleting a PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#deleting-a-personal-access-token)). No owner-facing delete endpoint exists in the OpenAPI description (source above).
- **Credential revocation API:** `POST /credentials/revoke` accepts fine-grained PATs (`github_pat_`), classic PATs, `gho_`, `ghu_`, and `ghr_` tokens. Up to 1000 tokens per request, 60 unauthenticated requests per hour. Authenticated requests return 403. GitHub notifies the credential owners. Revoked credentials cannot be reactivated. GitHub says the endpoint "is intended to revoke credentials the caller does not own" ([GitHub Docs: Revocation](https://docs.github.com/en/rest/credentials/revoke)). See the open questions about an owner using it on their own token.
- **Automatic revocation:** GitHub revokes a token at its expiration date, when someone pushes it to a public repository or gist, or after one year with no use ([GitHub Docs: Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)).
- **Expiry header:** GitHub announced a `GitHub-Authentication-Token-Expiration` response header for PATs ([GitHub Changelog, 2021-07-26](https://github.blog/changelog/2021-07-26-expiration-options-for-personal-access-tokens/)). I could not fetch this page (the sandbox network policy blocked `github.blog`). See the open questions.
- **Permission discovery:** The `X-Accepted-GitHub-Permissions` response header lists the permissions that an endpoint needs. This helps you find the minimum permissions ([GitHub Docs: Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api)).

### 3. Fully automatable alternatives

#### GitHub App installation access tokens

- **Mint:** `POST /app/installations/{installation_id}/access_tokens`, with a JWT signed by the app private key ([GitHub Docs: Create an installation access token](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)). The JWT `exp` must be no more than 10 minutes in the future ([GitHub Docs: Generating a JWT](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)).
- **Down-scoping:** The `repositories` (names) or `repository_ids` body parameters limit the token to individual repositories, up to 500. The `permissions` object limits the permissions (for example `{"contents":"write","pull_requests":"write"}`). The token cannot get repositories or permissions that the installation does not have ([same source](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app); [GitHub Docs: Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)).
- **Lifetime:** "Installation tokens expire one hour from the time you create them." An expired token gives 401, and you must create a new token ([same source](https://docs.github.com/en/rest/apps/apps#create-an-installation-access-token-for-an-app)).
- **Revoke:** `DELETE /installation/token` revokes the token that authenticates the request ([GitHub Docs: Revoke an installation access token](https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token)).
- **Git:** Use the token as the HTTP password with the user name `x-access-token`. The app needs the "Contents" permission ([GitHub Docs: Authenticating as an installation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)).
- **Attribution:** "API requests made by an app installation are attributed to the app" ([same source](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)).
- **Token format change:** Since 2026-04-27, GitHub is rolling out a stateless installation token format (`ghs_APPID_JWT`). Tools that expect exactly 40 characters can fail ([GitHub Docs: Generating an installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)).
- **Refresh in a long-running sandbox:** Section 4 shows that `sbx secret set --command` re-runs the helper after the cache period (default 55 minutes). This is shorter than the 1-hour token lifetime.

#### GitHub App user access tokens (user-to-server)

- **Permissions:** A user access token has only the permissions and repositories that both the user and the app have ([GitHub Docs: Generating a user access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#about-user-access-tokens)).
- **Device flow:** Use it for headless and CLI tools. You must enable it in the app settings ([same source, device flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token)).
- **Lifetime:** The access token expires after 8 hours (`expires_in` 28800). The refresh token (`ghr_`) expires after 6 months (15897600 seconds). The `offline_access` scope gives an expiring token and a refresh token even if the app has expiry turned off (same source).
- **Refresh:** `client_secret` is required for a refresh unless the token came from the device flow ([GitHub Docs: Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)).
- **Down-scoping:** `POST /applications/{client_id}/token/scoped` makes a repository-scoped or permission-scoped user access token from a non-scoped one. Parameters: `access_token`, `target` or `target_id`, `repositories` or `repository_ids`, and `permissions`. "You must use Basic Authentication", with `client_id` as the user name and `client_secret` as the password ([GitHub Docs: Create a scoped access token](https://docs.github.com/en/rest/apps/apps#create-a-scoped-access-token)).
- **Revoke:** `DELETE /applications/{client_id}/token` revokes one token ([GitHub Docs: Delete an app token](https://docs.github.com/en/rest/apps/oauth-applications#delete-an-app-token)).

#### OAuth app tokens and `gh auth token`

- The `gh` CLI signs in with its own OAuth app ("GitHub CLI", client ID `178c6fc778ccc68e1d6a`). It requests the minimum scopes `repo`, `read:org`, and `gist` ([cli/cli internal/authflow/flow.go](https://github.com/cli/cli/blob/trunk/internal/authflow/flow.go)). `gh auth token` prints the token that `gh` uses ([cli/cli pkg/cmd/auth/token/token.go](https://github.com/cli/cli/blob/trunk/pkg/cmd/auth/token/token.go)). Thus `gh auth token` is not scoped per repository.
- `gh auth login --with-token` expects a classic PAT. For fine-grained PATs, the `gh` help text says "Favour setting `GH_TOKEN`" ([cli/cli pkg/cmd/auth/login/login.go](https://github.com/cli/cli/blob/trunk/pkg/cmd/auth/login/login.go)).
- OAuth app tokens do not expire until the user revokes them ([GitHub Docs: Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)). GitHub limits OAuth apps to ten tokens per user, app, and scope combination. GitHub revokes an older token when an app creates more ([GitHub Docs: Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation#token-revoked-due-to-excess-of-tokens-for-an-oauth-app-with-the-same-scope)).
- GitHub recommends a GitHub App for long-lived integrations and PATs only for "API testing or short-lived scripts" ([GitHub Docs: Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app#choosing-between-a-github-app-or-a-personal-access-token)).

### 4. Docker Sandboxes secrets

- **Injection:** A proxy on the host intercepts outbound requests from the sandbox and overwrites the auth header with the credential from the host. The sandbox sees only a sentinel value such as `proxy-managed` ([Docker Docs: Manage credentials](https://docs.docker.com/ai/sandboxes/configuration/credentials/)). The `github-clone` kit says the GitHub sentinel is `GH_TOKEN=gho_sbxproxymanaged000000000000000000000` ([docker/sbx-kits-contrib github-clone/README.md](https://github.com/docker/sbx-kits-contrib/blob/main/github-clone/README.md)).
- **`github` service domains:** `api.github.com`, `github.com`, `raw.githubusercontent.com`, `gist.github.com`, `copilot.github.com`, `api.githubcopilot.com`. Environment variables: `GH_TOKEN`, `GITHUB_TOKEN` ([Docker Docs: Built-in services](https://docs.docker.com/ai/sandboxes/configuration/credentials/#built-in-services)). The service does not inject into `npm.pkg.github.com` (same source).
- **Scope:** Service secrets are global by default. `--sandbox <name>` scopes a secret to one sandbox. Sandbox-scoped secrets take precedence over global secrets. Removing a sandbox-scoped secret restores the global secret ([Docker Docs: Store a secret](https://docs.docker.com/ai/sandboxes/configuration/credentials/#store-a-secret)).
- **Live updates:** "Adding, updating, or removing a service secret takes effect in existing local sandboxes without a restart, including secrets configured with `--command` or `--ref`" ([same source](https://docs.docker.com/ai/sandboxes/configuration/credentials/#store-a-secret); also [Docker Sandboxes release notes](https://docs.docker.com/ai/sandboxes/release-notes/)).
- **Rotation mechanism (`--command`):** `sbx secret set github --command '<cmd>'` stores a command, not a value. The daemon runs the command through the host shell, trims its output, and caches it for 55 minutes by default. `--refresh <duration>` changes the cache period, and `--refresh on-demand` runs the command for every credential use ([Docker Docs: Use a dynamic secret source](https://docs.docker.com/ai/sandboxes/configuration/credentials/#use-a-dynamic-secret-source); [sbx secret set reference](https://github.com/docker/docs/blob/main/data/sbx_cli/sbx_secret_set.yaml)). `--ref` supports 1Password `op://` references and AWS Secrets Manager ARNs (same sources).
- **Helper safety:** The command runs from a fresh temporary directory on the host. Use an absolute path, and keep the helper and its configuration outside writable sandbox mounts. `sbx` does not confine the helper ([sbx secret set reference](https://github.com/docker/docs/blob/main/data/sbx_cli/sbx_secret_set.yaml)). `sbx` verifies the source when you register it, unless you use `--no-verify` ([Docker Docs: Use a dynamic secret source](https://docs.docker.com/ai/sandboxes/configuration/credentials/#use-a-dynamic-secret-source)).
- **Flags of `sbx secret set`:** `--sandbox`, `--command`, `--ref`, `--refresh`, `--no-verify`, `--show-error`, `-t/--token` ("less secure: visible in shell history"), `-f/--force`, `--oauth` (openai only), and registry flags. Stdin input also works (`echo "$X" | sbx secret set anthropic`) ([sbx secret set reference](https://github.com/docker/docs/blob/main/data/sbx_cli/sbx_secret_set.yaml)).
- **Environment files:** An `sbxenv.yaml` file can declare `secrets.github.command` and `refresh` at sandbox scope. Changes to `secrets` apply only when you create the sandbox again ([Docker Docs: Sandbox environment files](https://docs.docker.com/ai/sandboxes/configuration/environment-files/#secrets)).
- **Storage:** macOS Keychain, Windows Credential Manager, or Linux Secret Service, with a file fallback under `~/.config/com.docker.sandboxes` ([Docker Docs: Where secrets are stored](https://docs.docker.com/ai/sandboxes/configuration/credentials/#where-secrets-are-stored)). `sbx reset` deletes all stored secrets (same source).
- **Kits:** A kit can declare its own `github` credential with per-domain injection rules. The `github-clone` kit injects `Authorization: Bearer %s` for `api.github.com` and uses user name `x-access-token` for `github.com`. It routes Git HTTPS through `gh auth git-credential` ([docker/sbx-kits-contrib github-clone/spec.yaml](https://github.com/docker/sbx-kits-contrib/blob/main/github-clone/spec.yaml)). The `x-access-token` user name is the same one that GitHub documents for installation tokens over Git ([GitHub Docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)). I found no kit in `docker/sbx-kits-contrib` that mints GitHub App tokens ([repository tree](https://github.com/docker/sbx-kits-contrib)).

### 5. Tooling to open the URL or read the token, and token count limits

- I found no `gh` command or other official GitHub tool that opens the fine-grained PAT pre-fill URL or reads the generated token back. The `gh` source copies only the device-flow one-time code to the clipboard ([cli/cli internal/authflow/flow.go](https://github.com/cli/cli/blob/trunk/internal/authflow/flow.go)). For classic PATs, the docs describe a manual copy button ([GitHub Docs: Creating a PAT (classic)](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-personal-access-token-classic)). A semi-manual flow is possible: a script opens the pre-fill URL in a browser, you select repositories and click **Generate token**, and then you pipe the clipboard into `sbx secret set github --sandbox <name>` (stdin input is documented in the [sbx secret set reference](https://github.com/docker/docs/blob/main/data/sbx_cli/sbx_secret_set.yaml)).
- **Limits:** 50 fine-grained PATs per user ([GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token)). Ten OAuth app tokens per user, app, and scope combination, and ten new tokens per hour ([GitHub Docs: Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation#token-revoked-due-to-excess-of-tokens-for-an-oauth-app-with-the-same-scope)). I found no documented count limit for installation access tokens.

## Open questions and unconfirmed items

- **UNCONFIRMED: Owner use of `/credentials/revoke`.** The docs say that the endpoint is "intended" for credentials that the caller does not own. The docs do not say that it rejects the owner's own token. It sends a notification to the owner. Test before you depend on it for cleanup.
- **UNCONFIRMED: `GitHub-Authentication-Token-Expiration` header.** The only source is the GitHub Changelog (2021-07-26), which I could not fetch. A web search summary reported its content. The header name and its behavior for fine-grained PATs and app tokens need a test.
- **UNCONFIRMED: Changelog for template URLs.** I could not fetch [Template URLs for fine-grained PATs and updated permissions UI (2025-08-26)](https://github.blog/changelog/2025-08-26-template-urls-for-fine-grained-pats-and-updated-permissions-ui/) or [optional expiration for fine-grained PATs (2024-10-18)](https://github.blog/changelog/2024-10-18-new-pat-rotation-policies-preview-and-optional-expiration-for-fine-grained-pats/), because the sandbox network policy blocks `github.blog`. A search summary says that the template URL "captures the permissions, resources, lifetime, and details". "Resources" can mean the resource owner only. The docs table has no repository parameter.
- **UNCONFIRMED: Header format of the built-in `github` service on `github.com`.** The docs do not say which header the built-in service writes for Git HTTPS traffic. The `copilot` kit uses `Bearer %s` for `github.com`, and the `github-clone` kit uses Basic with `x-access-token`. Test `git push` with an installation token through the built-in service.
- **UNCONFIRMED: `-g` flag.** The `github-clone` README and the Docker authentication workflow page mention `sbx secret set -g github`. The CLI reference YAML has no `-g` flag. Global is the default scope for service secrets.
- **UNCONFIRMED: Lifetime of scoped user access tokens.** The `/token/scoped` response has an `expires_at` field. The docs do not state whether the scoped token keeps the 8-hour lifetime of its parent token.
- **Not researched:** GitHub Enterprise Cloud enterprise-level PAT endpoints and policies.
